# Hopdock — инструкция для продолжения работы

Составлено 13 октября 2026 года по требованиям пользователя в этом чате. Читать перед изменениями проекта. Это постоянный контекст продукта; новое прямое указание пользователя может изменить прежнее решение. Не выдавать технические детали текущей реализации за отдельные требования пользователя.

## Как работать с пользователем

- Общаться по-русски, коротко и по делу. Когда пользователь говорит «делай», «добавь», «почини», выполнять работу до проверенного результата.
- Сначала изучать существующий код и сохранять уже согласованный дизайн. Не начинать очередной редизайн без запроса.
- Коротко сообщать о существенных изменениях и результатах проверки. Не называть функцию работающей, если проверен только внешний вид или mock.
- Если пользователь просит запустить приложение, запускать актуальную сборку. При смене запущенной сборки закрывать прежнее окно штатно; не завершать все процессы Electron/Node подряд.
- Не терять пользовательские данные. Для проверок использовать отдельные профили и локальный SSH-сервер; не добавлять тестовые записи в рабочее хранилище.

## Дизайн: приоритеты и принятый стиль

- Дизайн — один из главных приоритетов. Интерфейс должен выглядеть как продуманное рабочее приложение, без ощущения шаблонного «ИИ-дизайна».
- Termius служит ориентиром для раскладки хостов, групп, терминала и панели сниппетов. Не копировать автоматически все его цвета и функции.
- Пользователю нравится компактная раскладка Termius: группы отдельным блоком, ниже сетка невысоких горизонтальных карточек серверов. Не превращать серверы в большие плитки и не тратить полезную площадь на пустые отступы.
- Использовать настоящие иконки групп/папок для групп. Иконки серверов или операционных систем относятся к хостам, не к группам.
- При SSH-подключении автоматически определять ОС и дистрибутив, сохранять результат у хоста и обновлять значок карточки/вкладки. Определять в отдельном ограниченном exec-канале, не писать служебные команды или `exit` в рабочий терминал. Учитывать fish, RouterOS, Windows, macOS/BSD и Linux os-release. Серверный banner — только запасная подсказка; неизвестную ОС не выдумывать. Ошибка определения не должна обрывать SSH-сессию.
- Поддерживать светлую и тёмную темы с одинаково аккуратной геометрией и читаемостью.
- После экспериментов с типографикой в духе Claude пользователь выбрал **Lora**. Сохранять это направление, не менять шрифт произвольно.
- Соблюдать отступы между секциями, полями, карточками настроек и пояснениями. В частности, блоки настройки синхронизации и «What syncs» не должны слипаться.
- Логотип выбран из вариантов, созданных генерацией изображений: **первый вариант**. Использовать существующий утверждённый знак Hopdock в приложении, иконке и брендинге.
- Пользователь попросил больше красивых анимаций и поиск примеров в интернете. Добавлять согласованные движения панелей, списков, меню, вкладок, уведомлений и отклик кнопок; проверять, что они не мешают работе и выделению текста.

### Текущая реализация дизайна — опора, а не обязательный новый макет

- Тёплая спокойная палитра: тёмные серо-оливковые поверхности, светлая фарфоровая тема, приглушённый зелёный акцент.
- Lora используется в брендинге; основной интерфейс — Source Sans 3, терминал и код — JetBrains Mono.
- Общие токены и анимации находятся в `packages/ui/src/tokens.css`. Использовать их вместо независимых цветов, размеров и эффектов для каждого экрана.
- Утверждённый знак: `packages/ui/src/assets/hopdock-mark.svg`; исходные концепты — `docs/design/logos/`.
- Анимации в основном используют CSS opacity/transform; переходы разделов — Web Animations API. Системный `prefers-reduced-motion` учитывается. Не добавлять тяжёлую библиотеку только ради простого эффекта без необходимости.

## Диалоги и боковые формы

- **Не должно быть системных диалогов сообщений**: никаких `alert`, `confirm`, `prompt`, системного выбора алгоритма ключа через OK/Cancel и подобных окон.
- Более позднее явное исключение пользователя: **выбор и сохранение файлов должны быть системными**. Использовать нативный Open/Save file picker; встроенный файловый диалог не нужен.
- Все формы New/Edit и аналогичные действия оформлять в едином стиле правой боковой панели, как Edit key. Применять общий `Drawer`, а не создавать очередное центральное модальное окно.
- Сохранять ввод при ошибке; ошибки должны отображаться в самой форме понятным образом.
- При выделении текста, когда мышь зажата внутри панели и затем выведена за её границы, панель **не должна закрываться**. Закрытие по фону допускается только для самостоятельного клика, начавшегося и закончившегося на фоне.
- Сохранять клавиатурную навигацию, фокус внутри открытой формы, Escape и восстановление фокуса после закрытия.
- Готовые решения: `Drawer.tsx`, `KeyDetails.tsx`, `TextPrompt.tsx`, `useBackdropDismiss.ts`, `FilePicker.tsx`.

## Хосты и группы

- Должна быть настройка скрытия из общего списка Hosts тех хостов, которые уже входят в существующую группу. Внутри группы её хосты остаются видны.
- Создание групп должно быть легко найти. Принятый вариант: стрелка рядом с **New host → New group**, как в примере Termius.
- При создании хоста можно сразу выбрать группу. Должен быть вариант без группы.
- Новую группу можно создать прямо из поля Group, не потеряв остальные заполненные поля хоста.
- Если хост создаётся внутри открытой группы, выбирать эту группу заранее. При редактировании сохранять прежнюю группу и позволять поменять или убрать её.
- Не назначать новый хост в первую попавшуюся группу автоматически.
- Поддерживать drag and drop карточки хоста в группу и обратно в «Без группы», с подсветкой цели. Перенос сохраняет пароль/ключ и запускает автосинхронизацию; отменённое перетаскивание не меняет данные и не открывает SSH-сессию. Выбор Group в форме остаётся доступной с клавиатуры альтернативой.

### Авторизация хоста

- **Не показывать отдельный выбор Auth** с Password / SSH key / SSH key + password.
- В форме всегда есть поле пароля и выбор SSH-ключа. Для создания/сохранения требуется хотя бы одно из них; можно указать оба.
- Тип подключения определять автоматически по заполненным полям. При наличии ключа и пароля поддерживать их совместное использование, как в Termius.
- Пароль учётной записи сервера и passphrase приватного ключа — разные значения; не смешивать их.
- При редактировании пустое поле пароля должно сохранять уже записанный пароль. Удаление сохранённого пароля должно быть явным действием.
- В карточках хостов не показывать пароль, маску или глаз: пользователь убрал этот элемент после просмотра. Просмотр/скрытие пароля через глаз оставить в форме хоста. Сохранённый пароль читать только по явному нажатию; по умолчанию и при повторном открытии он скрыт.
- Реализованные способы авторизации и их ограничения проверять по коду. Вопрос пользователя о сертификатной авторизации сам по себе не был требованием реализовать её.

## Keychain и WinSCP

- Keychain — обязательная часть приложения и синхронизации, а не декоративный раздел.
- При нажатии на ключ открывать правую панель редактирования, близкую по удобству к присланному примеру Termius: имя, приватный и публичный ключи, passphrase, копирование, сохранение изменений.
- Поддерживать экспорт приватных ключей через системный Save picker. Сохранять рабочий экспорт в исходном формате и PuTTY `.ppk`, используемый WinSCP.
- WinSCP-интеграция должна работать с сохранёнными учётными данными хоста. Пользователь указал свой репозиторий как ориентир: https://github.com/king-of-Jupiter/termorator.
- Не показывать пароли и приватные ключи в сырых ошибках, логах и выводах инструментов. Секреты читать только там, где они нужны для конкретного действия.

## Терминал и сниппеты

- Терминалу нужно максимум полезной площади, как в присланных скриншотах Termius. Избегать больших обрамлений, лишних панелей и повторяющихся заголовков соединения.
- **Focus terminal пользователю не нужен.** Не возвращать этот режим, кнопку разворачивания или перехват Ctrl+Shift+F без нового запроса.
- Справа от терминала нужна функциональная панель сниппетов: папки, поиск, короткое превью команды, создание/редактирование/удаление и запуск.
- Панель можно скрыть, чтобы освободить площадь терминала. При скрытии/открытии и редактировании сниппетов сохранять текущую SSH-сессию.
- Команду из правой панели отправлять в **текущую оболочку**, сохраняя рабочий каталог и окружение; результат должен появляться в терминале. Не заменять это запуском через отдельное временное SSH-соединение.
- Для переменных сниппета сначала открывать поля заполнения; затем отправлять подставленную команду в текущий терминал.
- При изменении доступной площади обновлять размеры PTY, а не переподключаться.
- Текущая геометрия для ориентира: вкладки около 44 px, статус около 20 px, панель сниппетов около 300 px. Сами числа — деталь реализации; основное требование — компактность и полезная площадь.

## Ошибки и обратная связь

- Пользователь потребовал понятную обработку ошибок для разных сценариев. Не оставлять маленькую красную строку сверху и не выводить сырые Electron IPC-исключения.
- Давать конкретное сообщение: что произошло, что пользователь может сделать, и при необходимости повтор действия или переход в нужный раздел.
- Использовать существующие оформленные `ErrorNotice`, `ErrorNotifications` и каталог `packages/core/src/errors.ts`; добавлять туда новые категории ошибок.
- Отдельно учитывать неверный пароль, отсутствующий приватный ключ на устройстве, неверную passphrase, потерю соединения, проблемы сети/файлов, синхронизации, обновления и импорта.
- Не терять сохранённые данные при ошибках чтения, валидации или записи. Не подменять повреждённое хранилище пустой библиотекой без объяснения.

## Синхронизация и конфигурация

- Обязательно синхронизировать **пароли хостов, Keychain и Snippets**, а также хосты и группы. На другом устройстве восстановленные данные должны быть пригодны для использования.
- Сохранять существующее сквозное шифрование паролей, приватных ключей, passphrase и содержимого сниппетов. Не отправлять их открытым текстом.
- **Supabase URL задаётся при сборке**, а не пользователем в обычной форме настроек. Публичный ключ также берётся из конфигурации сборки/CI.
- Пользователь привязал Supabase к GitHub-репозиторию Hopdock. Актуальные настройки искать в `.env.example`, build-конфигурации и CI; не копировать секреты в инструкционные файлы.
- Сохранять независимость пароля аккаунта синхронизации и пароля шифрования хранилища.
- Вход в аккаунт — отдельный экран при первом запуске и кнопка аккаунта в боковой навигации, а не поля email/пароля в настройках. Оставлять возможность Continue offline. Успех показывать после реальной проверки Supabase; сохранять сессию через защищённое хранилище ОС, не пароль аккаунта. Выход останавливает облако и сохраняет локальную библиотеку. Настройки содержат шифрование и статус синхронизации; не смешивать библиотеки разных аккаунтов молча.
- Не ломать синхронизацию удалений или новых групп после первоначальной миграции.
- После создания, изменения и удаления сразу запускать фоновую синхронизацию без обязательного Sync now. Быстрые последовательные правки можно объединять короткой задержкой; ошибка сети не должна терять локальные изменения. Не отправлять неизменённые версии повторно. Счётчики должны отражать изменённые записи, время — сравниваться как даты, а не сырые строки Z/+00:00.

## Версия и автообновления

- В месте, где отображается `hopdock <версия>`, должен быть также короткий идентификатор Git-коммита, использованного при сборке. Не хардкодить устаревший commit.
- Пользователь попросил исправить автообновления и явно разрешил сделать **репозиторий Hopdock публичным** для распространения через GitHub Releases. Это разрешение относится к этому репозиторию, не к любым другим проектам.
- Автообновления должны действительно проверять, скачивать и устанавливать опубликованные релизы. Состояние проверки, прогресс и готовность к перезапуску не должны теряться при переходах между разделами.
- При ручном перезапуске для установки учитывать активные соединения. Не публиковать неполный релиз, пока не готовы необходимые артефакты.
- Проверять updater Hopdock, а не обновления приложения Codex.
- В любой упакованной сборке, включая `electron-builder --dir`, должен быть `resources/app-update.yml`. Он явно включён через extraResources из `apps/desktop/build/app-update.yml`; не полагаться только на генерацию конфигурации при создании установщика. Отсутствие конфигурации обновления не должно отображаться как ошибка пользовательского файла.

## Импорт из Termius

- Изучать существующий импорт в **king-of-Jupiter/termorator**, который пользователь указал как источник подхода.
- Последнее уточнение пользователя: **одна кнопка в настройках, не более**. Не добавлять импорт в меню хостов, отдельный мастер или набор лишних действий.
- Последнее требование: **Settings → Import from Termius** должна сама находить локальный профиль Termius и импортировать его. Не спрашивать JSON, не просить пользователя запускать экспортёр или устанавливать Python.
- Ридер IndexedDB и расшифровки встроен в сборку отдельным исполняемым модулем. Пароли и ключи передаются в main-процесс через pipe; пользовательский экспортный файл не создаётся. После импорта результат и примечания появляются в настройках.
- Инструкция экспортёра: https://github.com/king-of-Jupiter/termorator/blob/main/tools/termius-to-termorator/README.md.
- Переносить хосты, пароли, доступные приватные ключи и passphrase, связи ключей с хостами, группы и сниппеты. Повторный импорт не должен дублировать записи или перетирать локальные изменения.
- В новых профилях Termius учитывать local_id из ключа IndexedDB и таблицы ssh_config_identities/ssh_config_identities_shared. Повторный импорт может восстановить авторизацию ранее неполной импортированной записи только при пустом логине, auth=agent, неизменном адресе/порте и отсутствии сохранённого пароля; имеющиеся данные не заменять.
- Текущее ограничение: вложенные пути групп/пакетов сохраняются как полные имена `Production / Europe`; прокси, agent forwarding и пробросы портов отмечаются как не перенесённые. Не утверждать, что эти настройки работают после импорта.
- Не изменять профиль Termius. При невозможности прочитать или расшифровать профиль не менять библиотеку Hopdock; давать конкретное сообщение. Данные миграции могут содержать открытые секреты; не сохранять их в репозитории или логах.

## Тестовые данные и проверка работоспособности

- **В рабочем приложении не должно быть тестовых/демонстрационных данных.** Новое хранилище и обычное браузерное превью должны начинаться пустыми.
- Mock-данные разрешены только в явно включённых тестовых сценариях. Не возвращать автоматическое заполнение примерами при запуске или чтении неполной записи.
- Пользователь просил проверить все функции приложения с локальным SSH-сервером. Для изменений авторизации, терминала, Keychain, SFTP, WinSCP, сниппетов, синхронизации и импорта проверять реальное поведение подходящими тестами.
- В проверках учитывать отмену файлового диалога, повторные операции, ошибки, сохранение данных, переподключение, resize и двоичные файлы, когда это относится к изменению.
- Для визуальных изменений проверять обе темы, реальные размеры окна и взаимодействия. После анимаций особо проверять выделение текста и сохранение соединения.
- Не выдавать результаты mock-теста за проверку настоящего SSH, WinSCP или облака. Сообщать существенные ограничения проверки.

### Полезные команды и ориентиры

Рабочий стек: Electron + React + TypeScript. Main/preload/renderer — в `apps/desktop`, UI — в `packages/ui`, модели и ошибки — в `packages/core`, SSH — в `packages/ssh`.

```text
npm run typecheck
npm run build --workspace apps/desktop
npm run test:ui
npm run test:desktop
npm run test:ssh
npm run test:winscp
npm run test:updates
npm run test:updates:real
```

Выбирать проверки по изменению; не запускать всё механически для правки текста. Последняя проверка 14 октября 2026 года: 30 сценариев Electron и 19 браузерных проверок прошли. Это исторический результат, не гарантия для будущих изменений.

Для Windows собирать в отдельный каталог `dist/<имя-изменения>`, чтобы запущенный `.exe` не блокировал упаковку. Сначала дождаться завершения production build, затем запускать electron-builder. Не считать сборку опубликованным релизом: commit/push/release — отдельные действия.

Не терять существующие незакоммиченные изменения: в этой сессии накоплено много пользовательских функций. Перед работой смотреть состояние Git; не делать reset/clean и не коммитить всё скопом без соответствующей задачи.

Подробные описания уже реализованных решений:
