# Vault sync

Sign in from the welcome screen or the **Account** button in the sidebar, then save a separate **Sync encryption password** (at least 12 characters) in Settings on each device. Continue offline is available without an account. Sign-in is validated by Supabase before the UI reports success. Access/refresh tokens are persisted through Electron safeStorage; the account password is not retained after sign-in. Existing legacy credentials migrate to a saved session on successful sync. Sign-out stops cloud sync and removes this device's session while preserving its local library. A library linked to another account cannot be silently uploaded to a different account. The Supabase project URL and public key are embedded at build time and cannot be selected from Settings or overridden by IPC. Use the same encryption password everywhere. Choose a strong passphrase and keep it safe; recovery and key rotation are not supported. The account password can change independently.

Create account uses Supabase signup. Projects with email confirmation enabled show an email confirmation notice instead of claiming the user is signed in; after confirming, return to Hopdock to sign in. Registration availability and email delivery are controlled by the Supabase project. Auth tests use the real SDK against a local service fixture, including failed sign-in, confirmation-required signup, session restore after an Electron restart and sign-out.

Build configuration is loaded from the repository-root `.env.local` or environment variables: `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY`. Copy `.env.example` for local development. GitHub Actions reads repository variables with those names for both build and release workflows. Release builds require both values; offline development builds may omit both. Only modern public `sb_publishable_` keys are accepted. Never put an account password, encryption password or server secret key in these build variables.

The GitHub integration uses `supabase/config.toml` and `supabase/migrations/`. Its working directory is `.`. Enable **Deploy to production** in the Supabase integration to apply migrations after a push/merge to its configured production branch. The initial migration creates `public.vault_items`, enables owner-based RLS and grants authenticated CRUD access. Public-key access without a signed-in account cannot read other users' rows. `supabase/schema.sql` is retained as the manual setup equivalent. Repository connection alone does not configure the Electron build or run unpushed migrations.

Click **Sync now** to migrate existing saved host passwords, Keychain keys (including private material and passphrases), and Snippets as well as subsequent edits. Received passwords and key passphrases are restored to local Electron safeStorage; private key files are restored under this device's keys directory. Received keys are available for SSH and SFTP immediately. Snippet names, folders, scripts and variables are transferred together. The UI reloads all libraries after sync. Deleted hosts, keys and snippets are uploaded as tombstones, without encrypted content.

Secret content uses AES-256-GCM with a random 12-byte nonce and a 16-byte salt, a 32-byte key derived with scrypt (N=32768, r=8, p=1), and authenticated vault/item identity and content type. Host passwords, key material with passphrases, and complete snippets have separate encryption domains. Only versioned envelopes are uploaded inside the existing item JSON; no schema migration is necessary. The encryption passphrase stays in local safeStorage and is never sent to Supabase. Host metadata and public key details remain plaintext under the existing account RLS. Items exceeding 3 MB of plaintext are rejected before upload.

An incorrect passphrase or damaged ciphertext aborts the operation before uploads or local changes. Missing secret fields from older metadata-only records preserve local secrets. Legacy plaintext snippets are read and rewritten encrypted on the first content migration. Pull reads a complete paginated snapshot so an older edit time from another device cannot be missed. Dates are normalized, and per-record acknowledged versions prevent repeated uploads. Counts report changed records; last sync is the completion time, not the newest record's edit time. Keep all devices on the updated application: older clients do not preserve encrypted fields. Remote file paths are never trusted; private keys use validated item IDs and local paths.

Local saves schedule automatic sync after a 300 ms debounce. Runs are serialized, failed uploads retry after 15 seconds, and startup/incoming checks run automatically (incoming polling every 15 seconds). Sync now remains available. Local changes made during network requests invalidate the old snapshot; remote files/secrets are not committed, and a fresh run merges the current library. Status changes and completed vault updates are sent to the renderer without resetting SSH sessions. Tests use isolated profiles and a local HTTP fixture with the actual Supabase SDK; this is not a live Supabase service test.

Verification: `npx tsx --test apps/desktop/src/main/password-sync.test.ts`. Tests cover migration, two-device restoration and updates, Unicode, ciphertext randomization, wrong keys, tampering, identity binding, failed uploads, legacy records and deletions. Keychain tests use real encrypted RSA key files and prove the restored key can sign a message whose signature verifies against the original public key. These tests use an in-memory transport; they do not authenticate to a live Supabase project.
